## 📌 Overview

**Problem:** Choosing between ensemble machine learning methods is rarely
a fair comparison in practice — different teams tune different models to
different degrees, on different feature sets, and report whichever number
looks best. This framework removes that ambiguity by benchmarking
**Random Forest, XGBoost, and SVM** under identical conditions: the same
engineered features, the same feature selection, the same class-imbalance
handling, the same cross-validation strategy, and the same evaluation
metrics.

**Approach:** A modular, config-driven pipeline takes raw tabular data
through preprocessing, feature engineering, feature selection, and class
imbalance handling, then runs automated hyperparameter tuning
(`GridSearchCV` with Stratified K-Fold CV) for each model before scoring
them all on a common held-out test set. Built during a Machine Learning
internship at **Arch Technologies**.

**Key Results:**

| Metric | Value |
|---|---|
| Records processed | 50,000+ |
| Feature engineering improvement | **+35%** model input quality |
| Hyperparameter tuning | Automated via `GridSearchCV` |
| F1-score improvement | **+12%** via feature selection + imbalance handling |
| Models benchmarked | Random Forest, XGBoost, SVM |

## ✨ Features

- **Modular model interface** — every model implements a shared
  `BaseModel` abstract class (`build_estimator`, `param_grid`, `fit`,
  `predict`, `save`/`load`), so adding a new model never touches the
  tuning or benchmarking code.
- **Automated hyperparameter tuning** — a `GridSearchCV` wrapper
  (`src/tuning/grid_search.py`) with a consistent scoring metric and CV
  strategy across every model.
- **Cross-validation strategies** — Stratified K-Fold throughout, both
  inside tuning and as a standalone post-hoc validation utility.
- **Class imbalance handling** — SMOTE oversampling and balanced class
  weights, applied correctly (training data only, no leakage).
- **Feature selection** — variance filtering plus a choice of Random
  Forest importance or ANOVA F-value (`SelectKBest`) selection.
- **Comprehensive benchmarking** — one `Benchmark` orchestrator tunes,
  fits, evaluates, and reports on every registered model in a single
  call, producing a ready-to-read comparison table and figure set.

## 🚀 Quick Start

### Installation

```bash
git clone https://github.com/mawawazir/ml-ensemble-benchmarking.git
cd ml-ensemble-benchmarking
make install
```

`make install` runs `pip install -r requirements.txt` followed by
`pip install -e .` (editable install of the `src` package).

### Running the Benchmark

```bash
make benchmark
```

This runs the full pipeline — load → preprocess → engineer features →
select features → balance classes → tune → evaluate — across Random
Forest, XGBoost, and SVM, then writes results to
`reports/benchmark_results.json` and figures to `reports/figures/`.

### Running with a Custom Config

```bash
python -c "
from src.config import load_config
from src.models.benchmark import Benchmark
from src.models.random_forest import RandomForestModel
# see docs/benchmarking_guide.md for the full worked example
"
```

Or point the default config at your own dataset:

```yaml
# configs/default.yaml
data:
  raw_path: "data/raw/your_dataset.csv"
  target_column: "your_target_column"
```

See [`docs/benchmarking_guide.md`](docs/benchmarking_guide.md) for
complete worked examples, including single-model tuning and custom
hyperparameter grids.

## 📊 Dataset

The framework works with any tabular binary-classification dataset. By
default (when `data.raw_path` is left `null` in `configs/default.yaml`),
it synthesizes a reproducible **50,000-record** dataset via
`sklearn.datasets.make_classification` (`random_state=42`):

| Property | Value |
|---|---|
| Rows | 50,000 |
| Numeric features | 20 |
| Categorical features | 2 (`category_region`, `category_channel`) |
| Target | Binary, ~15% positive class (imbalanced) |
| Missing values | ~3% of one feature, injected intentionally |

This keeps the entire pipeline runnable end-to-end without requiring a
proprietary dataset to be committed to the repository, while remaining
fully reproducible. To use your own data, see
[Quick Start](#-quick-start) above and [`data/README.md`](data/README.md).

## 🔬 Methodology

Full detail in [`docs/methodology.md`](docs/methodology.md); summary below.

- **Feature engineering pipeline** (+35% input quality): interaction
  terms, polynomial (squared) terms, ratio features, and row-wise
  statistical aggregates, all derived from the preprocessed numeric
  columns.
- **Feature selection**: variance-threshold filtering followed by either
  Random Forest importance (default) or ANOVA F-value (`SelectKBest`).
- **Class imbalance handling**: SMOTE oversampling (training data only)
  or balanced class weights — never both at once.
- **GridSearchCV strategy**: exhaustive search over each model's
  hyperparameter grid, F1-score as the selection objective, `refit=True`.
- **Cross-validation**: Stratified K-Fold everywhere (default 5 folds),
  preserving class proportions across folds given the target imbalance.
- **Evaluation metrics**: accuracy, precision, recall, F1-score,
  ROC-AUC, and confusion matrix — computed identically for every model
  via one shared function.

## 📈 Benchmark Results

| Model | Accuracy | Precision | Recall | F1-Score | ROC-AUC | CV Score (F1) | Tuning Time |
|---|---|---|---|---|---|---|---|
| **XGBoost** | **0.964** | **0.871** | **0.909** | **0.889** | **0.973** | 0.972 | 4.09s |
| Random Forest | 0.949 | 0.832 | 0.845 | 0.839 | 0.972 | 0.964 | 36.75s |
| SVM | 0.839 | 0.493 | 0.813 | 0.614 | 0.902 | 0.842 | 43.43s |

### Per-Model Analysis

- **XGBoost** — strongest recall (0.909), critical when missing positive
  cases is costly on an imbalanced target. Also the fastest to tune by
  a wide margin, thanks to efficient histogram-based tree construction.
- **Random Forest** — nearly matches XGBoost on ROC-AUC (0.972 vs.
  0.973) but trails on F1 and recall; slowest tuning run due to a
  larger hyperparameter grid (216 combinations).
- **SVM** — noticeably lower precision (0.493), suggesting the `rbf`
  kernel struggles with this feature space's dimensionality; still
  achieves a respectable ROC-AUC (0.902), showing class separability
  exists but the decision threshold is miscalibrated for this imbalance.

### Winner and Why

**XGBoost** wins on every headline metric (F1, ROC-AUC) while tuning
roughly **9x faster** than Random Forest and **10x faster** than SVM,
making it the clear practical default for this dataset and problem shape.

### Training Time vs. Performance Tradeoff

XGBoost dominates the efficiency frontier — highest F1, lowest tuning
time. Random Forest is a reasonable middle ground when tree-count
robustness or Gini-importance interpretability matters more than a few
points of F1. SVM is dominated on both axes for this configuration.

Full discussion: [`docs/results.md`](docs/results.md).

## 🔍 Model Interpretation

- **Feature importance comparison**: the Random Forest's Gini importance
  (`reports/figures/feature_importance.png`) highlights which engineered
  features — including interaction and ratio terms — contribute most to
  splits, giving a quick, low-cost view of feature relevance.
- **Gini vs. permutation importance**: Gini importance (used by default,
  via `RandomForestClassifier.feature_importances_`) is fast but can be
  biased toward high-cardinality or correlated features. Permutation
  importance (`sklearn.inspection.permutation_importance`) is slower but
  model-agnostic and measures actual predictive contribution on held-out
  data — recommended as a follow-up check before trusting Gini rankings
  for feature-pruning decisions in production.

## ⚙️ Configuration

### YAML Config Explanation

`configs/default.yaml` holds settings shared across all models (data
paths, CV folds, output directories). Each model's config
(`configs/random_forest.yaml`, `configs/xgboost.yaml`,
`configs/svm.yaml`) is deep-merged on top of it, overriding only what it
needs — chiefly `model.base_params` and `model.param_grid`.

```yaml
# configs/random_forest.yaml (excerpt)
model:
  name: "random_forest"
  param_grid:
    n_estimators: [100, 200, 300]
    max_depth: [null, 10, 20, 30]
```

### How to Add a New Model

1. `make add-model NAME=my_model` scaffolds `src/models/my_model.py`
   and `configs/my_model.yaml`.
2. Implement `build_estimator()` and `param_grid()` in the new file.
3. Register the class in `src/models/__init__.py`.
4. Add tests in `tests/test_models.py`.

Full walkthrough: [`CONTRIBUTING.md`](CONTRIBUTING.md#adding-a-new-model).

### How to Modify Hyperparameter Grids

Edit the relevant YAML file's `model.param_grid` section, or override
at call time:

```python
model = RandomForestModel(param_grid_override={"n_estimators": [500]})
```

## 🧪 Testing

```bash
make test
```

Runs the full `pytest` suite (`tests/test_data.py`, `test_features.py`,
`test_models.py`, `test_tuning.py`) — 42 tests covering data loading and
preprocessing, feature engineering/selection/imbalance handling, all
three model wrappers plus the `Benchmark` orchestrator, and the
`GridSearchCV` tuning wrapper. CI runs this suite on Python 3.9, 3.10,
and 3.11 on every push and pull request (`.github/workflows/ci.yml`).
